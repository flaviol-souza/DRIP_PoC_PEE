DRIP ESP32 PoC — Project Reference Map
Purpose: a single reference for what each file does, how files depend on each other, and — critically — exactly where every piece of trust-chain data lives, ahead of the DNS integration work.

## PART 2 — Firmware files (ESP32 / Arduino)

### Entry point

**`DRIP\_Broadcast\_RID.ino`**
Main sketch. `setup()` initialises Wi-Fi/NVS, loads the UA keypair (`det\_load\_hardcoded`), builds the fake Apex→RAA→HDA→UA test chain (`drip\_reg\_init`, only if `DRIP\_TEST\_BE` is defined), and starts track playback. `loop()` runs the 3 Hz transmission cycle: gets the current position (from playback or the simulator), builds Basic ID + Location (+ System on Cycles A/C), then branches per `cycle\_phase` to attach a Wrapper (Cycle A), Link (Cycle B), or Manifest (Cycle C), and transmits via `beacon\_tx\_send()`. Also polls for serial commands and halts transmission at end-of-track or on `stop`.
*Depends on:* nearly everything below.

### Identity \& cryptography

**`det\_generator.h` / `det\_generator.cpp`**
Owns the **UA keypair** and the **one true DET derivation algorithm** (`det\_compute`, RFC 9374 §3.5.2/Fig 1). `det\_load\_hardcoded()` derives the public key from the seed, self-checks it, computes the DET, and initialises the Ed25519 signer. `det\_sign()` signs arbitrary bytes. `det\_to\_session\_id()` packs a DET into the ASTM Basic ID field.
*Used by:* the `.ino`, `drip\_registration.cpp` (for the three test parent keys — same function, different RAA/HDA), `drip\_auth.cpp`/`drip\_manifest.cpp` (via `det\_sign`).

**`cshake128.h` / `cshake128.cpp`**
Standalone cSHAKE128 (NIST SP 800-185) implementation. Used for **both** DET derivation and DRIP Manifest hashing — two unrelated purposes, same primitive.
*Used by:* `det\_generator.cpp`, `drip\_manifest.cpp`.

**`drip\_registration.cpp` / `.h`** *(compiled only if `DRIP\_TEST\_BE` is defined in `drip\_config.h`)*
Fabricates a **self-consistent, fake** Apex→RAA→HDA→UA trust chain for bench testing. Holds the three parent private keys, derives their DETs via the shared `det\_compute()`, and signs each Broadcast Endorsement (`make\_be`). `drip\_reg\_next\_link()` rotates which BE is sent on Cycle B (pattern: HDA,UA is sent 4/6 slots; RAA,HDA and Apex,RAA each 1/6). `drip\_reg\_hda\_ua\_sam()` supplies the BE:HDA,UA bytes the Manifest hashes.
*Depends on:* `det\_generator.h` (shared DET algorithm), `drip\_auth\_page.h` (LE helper).
*Used by:* the `.ino` (Cycle B), `drip\_manifest.cpp` indirectly (via the `.ino` passing `hu\_sam`).

### Message encoding (ASTM F3411-22a)

**`f3411\_messages.h` / `f3411\_messages.cpp`**
Defines the three ASTM message structs (`F3411BasicID`, `F3411Location`, `F3411System`) and their encoders. Also owns the **DRIP timing constants** (`DRIP\_EPOCH\_UNIX\_S`, `SIM\_DRIP\_TIME\_BASE`, `DRIP\_VNA\_OFFSET\_S`) and the SAM-type constants used everywhere else. `DronePosition` (the struct playback/flight\_sim produce) is defined here too.
*Used by:* nearly every other firmware file (it's the shared vocabulary).

**`message\_pack.h` / `message\_pack.cpp`**
The ASTM Message Pack container (up to 9 × 25-byte messages, 802.11 IE 255-byte limit). `message\_pack\_add()` appends a message; the type/count header is kept in sync automatically.
*Used by:* the `.ino` to assemble each cycle's pack; `drip\_auth.cpp` reads pack contents to compute Wrapper Evidence.

**`drip\_auth\_page.h` / `drip\_auth\_page.cpp`**
Shared ASTM Authentication Message paging helper — the one correct implementation of splitting an arbitrary SAM payload into page-0 (17 data bytes) + continuation pages (23 data bytes each), with the dedicated Last-Page-Index octet. `drip\_put\_le32()` (little-endian serialisation) also lives here.
*Used by:* `drip\_auth.cpp`, `drip\_link.cpp`, `drip\_manifest.cpp` — every DRIP auth format pages through this one function, so a paging bug can't diverge between formats.

### DRIP authentication (RFC 9575)

**`drip\_auth.h` / `drip\_auth.cpp`** — **DRIP Wrapper, Extended Transport (§4.3.2)**
Builds the 89-byte Wrapper SAM. Collects the pack's non-Auth messages (`collect\_evidence\_order`, stable-sorted ascending by ASTM type — our documented convention for the RFC's ordering ambiguity), signs `VNB‖VNA‖Evidence‖DET`, then transmits with Evidence **cleared**. `DRIP\_WRAPPER\_MAX\_PAGES = 5`.
*Used by:* the `.ino`, Cycle A only.

**`drip\_link.h` / `drip\_link.cpp`** — **DRIP Link / Broadcast Endorsement (§4.2)**
Serialises a `BroadcastEndorsement` struct (VNB, VNA, DET\_child, HI\_child, DET\_parent, Sig — 137 bytes with the SAM-type byte) and pages it via `drip\_auth\_page`. Does **not** sign — signing happens in `drip\_registration.cpp`, which owns the parent keys.
*Used by:* `drip\_registration.cpp` (serialisation), the `.ino` (Cycle B, via `drip\_link\_build\_be`).

**`drip\_manifest.h` / `drip\_manifest.cpp`** — **DRIP Manifest (§4.4)**
Owns the rolling hash-chain state (`DRIPManifestState`: `prev\_manifest\_hash`, `pack\_hash`, `link\_hash`). `drip\_manifest\_update\_pack()`/`update\_link()` hash the Wrapper's pack and the BE:HDA,UA SAM respectively (called from Cycle A / Cycle B). `drip\_manifest\_build()` (Cycle C) assembles Evidence (`Prev‖Curr(null)‖Link‖Pack`), computes and back-fills the self-hash, signs `VNB‖VNA‖Evidence‖DET`, and pages the 121-byte SAM into 6 pages.
*Used by:* the `.ino`, all three cycles (state updates in A/B, build in C).

### Transmission

**`beacon\_tx.h` / `beacon\_tx.cpp`**
Starts the ESP32 as an open, hidden 802.11 AP on channel 6 and injects the DRIP vendor-specific IE (`OUI FA-0B-BC`, type `0x0D`) into the AP's own beacon frames via `esp\_wifi\_set\_vendor\_ie()`. `beacon\_tx\_stop()` clears the IE (used to halt transmission without tearing down Wi-Fi).
*Used by:* the `.ino`, once per cycle (`beacon\_tx\_send`) and on halt (`beacon\_tx\_stop`).

### Flying path data

**`drone\_data.h`** *(generated file — not hand-written)*
Produced by `csv\_to\_drone\_data.py` from your spreadsheet. One `PROGMEM` array of `DronePoint {lat\_e7, lon\_e7, alt\_dm, ts\_unix}` per flight, plus a `DRONE\_FLIGHTS\[]` index table (`flight\_id`, points pointer, count, `det` identity slot — currently always `nullptr`).
*Used by:* `drone\_playback.cpp` only.

**`drone\_playback.h` / `drone\_playback.cpp`**
Selects and plays back a recorded flight. Advances one point per transmission cycle, but **paces by the point's real recorded time delta** (Option A — holds a position across multiple 3 Hz cycles until real elapsed time reaches the recorded interval; computes speed/heading from the true delta, not an assumed 0.333 s gap). Holds on the final point at end-of-track (does not loop) and signals `drone\_playback\_finished()`, which the `.ino` uses to halt transmission. Also owns the serial command menu (`list | info | next | reset | stop | <number>`) and the `DRONE\_REPLAY\_RECORDED\_TIME` test-only switch (Location message timestamp only — DRIP VNB/VNA are unaffected, they always use the live clock).
*Depends on:* `drone\_data.h`.
*Used by:* the `.ino` (replaces `flight\_sim` as the position source when available).

**`flight\_sim.h` / `flight\_sim.cpp`**
The original synthetic fallback: a 5-waypoint square route at a fixed base location, looped via `millis()`. Used automatically if `drone\_data.h` has no flights (or playback fails to initialise).
*Used by:* the `.ino`, only when `g\_use\_playback == false`.

### Configuration \& debug

**`drip\_config.h`**
One `#define DRIP\_TEST\_BE` — the single switch that must reach every `.cpp` file (placed in a shared header, not the `.ino`, because Arduino compiles each `.cpp` separately and an `.ino`-local `#define` wouldn't propagate).

**`drip\_time.h`**
`drip\_timestamp()` — the live DRIP-epoch clock (`SIM\_DRIP\_TIME\_BASE + millis()/1000`). This is what **every** VNB/VNA in Wrapper/Link/Manifest ultimately comes from.

**`drip\_debug.h` / `drip\_debug.cpp`**
Verbose serial dump of every transmitted pack: the full VSIE, the raw pack bytes, and an annotated breakdown of each message (including reassembling and labelling SAM payloads — Link/Wrapper/Manifest). This is the human-readable log your Python tools (`observer.py`, `make\_map.py`) parse as "Format L".

## PART 3 — Python observer / tooling files

### Core decode/parse layer

**`odid.py`**
The ASTM/DRIP byte-level decoder. Header/type dispatch, per-message decoders (Basic ID, **Location — full Table 6/7 fields**, Self-ID, Operator ID, System — *note: System's "timestamp" field is bogus, see Part 4*), Message Pack splitting, multi-page Authentication reassembly, and DRIP-specific SAM decoders (`decode\_link\_sam`, `decode\_manifest\_sam`). Also the three input-format parsers: **Format L** (ESP32 serial log / `drip\_debug.cpp` output), **Format W** (Wireshark bytes-only export), **Format B** (hand-authored flat hex). `reconstruct\_wrapper\_evidence()` mirrors the firmware's Evidence-ordering convention for signature verification.
*Used by:* everything else in this list.

**`det.py`**
Pure-Python, dependency-free DET reference implementation: from-scratch Keccak-f\[1600]/cSHAKE128, `compute\_det(pubkey, raa, hda, suite)`, `verify\_det\_binding()`. This is the **ground truth** the firmware's `det\_compute()` was corrected to match.
*Used by:* `observer.py` (DET binding check), `make\_vectors.py`, `make\_map.py` (indirectly, via odid).

**`ed25519.py`**
Pure-Python RFC 8032 Ed25519 (sign/verify/derive), validated against the RFC's own test vectors. Deterministic, so it produces byte-identical signatures to the firmware's rweather/Arduino Crypto library for the same key+message — this is what lets us verify firmware signatures without hardware.
*Used by:* `observer.py` (Wrapper/Link/Manifest signature checks), `make\_vectors.py`.

### Validation / reporting

**`errors.py`**
The error catalog — every `E-XXX-NN` code, its description, and the governing ASTM/RFC clause. No logic, just the registry `observer.py` reports against.

**`observer.py`**
The main CLI. Auto-detects input format, decodes, and runs all validators:

* **Structural** (`E-FMT-\*`, `E-PACK-\*`, `E-AUTH-\*`) — ASTM-level correctness.
* **`E-DET-01/02`** — DET prefix + DET↔key binding (via `det.py`).
* **`E-SIG-01`** — Wrapper signature (via `ed25519.py` + `odid.reconstruct\_wrapper\_evidence`).
* **`E-LINK-01..04`** — Link chain: child DET↔HI binding, VNB/VNA window, parent signature, walk to the **hardcoded test Apex anchor** (`APEX\_HI`/`APEX\_DET` — see the gap noted below).
* **`E-MAN-01..05`** — Manifest: signature, self-hash recomputation, cross-checks against observed packs/links, Prev/Curr chaining.
*Depends on:* `odid.py`, `errors.py`, `det.py`, `ed25519.py`.

**`make\_vectors.py`**
Reference encoder + self-test. Hand-builds valid and deliberately-broken ASTM/DRIP messages (mirroring the firmware's exact byte layouts and signing procedures), then asserts the observer flags exactly the expected error on each. This is what proves firmware↔observer agreement *before* flashing.
*Depends on:* `odid.py`, `observer.py`, `det.py`, `ed25519.py`.

### Visualization

**`flight\_tracks.py`**
Extracts per-drone position tracks from a capture. **Identity correlation is stateful across the whole capture** (a Basic ID persists as "current identity" until a new one appears — matches how a real RID receiver behaves; a strict same-pack rule was tried first and fragmented real captures). Groups by DRIP DET when present, otherwise a generic session-ID hex label (some real captures aren't DRIP-native).
*Depends on:* `odid.py`.

**`make\_map.py`**
CLI that calls `flight\_tracks.extract\_tracks()` and writes a **self-contained HTML file** (Leaflet + OpenStreetMap via CDN, no server) — coloured polyline per drone, start/end markers, popups, togglable legend. Point "time" comes from the nearest DRIP auth's VNB in the same pack (System's timestamp field is never used — see below).
*Depends on:* `flight\_tracks.py`.

### Data preparation

**`csv\_to\_drone\_data.py`**
Runs **on your PC only** (never on the ESP32). Reads your spreadsheet (handles the locale-formatted numbers, drops position outliers, caps each flight at 1080 points/6 min by decimating only if it exceeds that), and writes `drone\_data.h` for the firmware to compile in.

### Capture tooling

**`arduino\_logger.py`**
Captures the ESP32's serial output to a text file (consumed as "Format L" by the Python tools). **Just fixed:** previously reset the board on every connect (standard ESP32/pyserial DTR-RTS interaction), which is why only flight 0 was ever capturable. Now suppresses that reset and can optionally select a flight (or send any playback command) immediately after connecting, in one step.

## PART 4 — Known gaps and honest caveats (relevant to Saturday)

1. **The Apex trust anchor is duplicated by value, not by reference.** `drip\_registration.cpp` (firmware) and `observer.py` (Python) each hardcode matching Apex key material independently — they were simply born knowing the same test secret. Nothing in the project addresses *how* an observer would come to trust an Apex key in the real world. **This is the gap the DNS work is meant to fill** (RFC 9374 §5/§9.3 — DNS+DNSSEC as the mechanism for an observer to obtain and trust a key it didn't already know).
2. **`Per-drone identity is stubbed, not wired.** Every flight currently broadcasts the single shared UA DET regardless of which flight is selected. The `det` field exists in `drone\_data.h`'s `DroneFlight` struct and `drone\_playback\_det()` already returns it — but the binary/header format has no path to populate it yet, and the firmware's Basic ID always uses `g\_kp.det` directly rather than checking `drone\_playback\_det()`.
3. **`E-SEM-01`'s cross-pack false positive was never relaxed** (flagged early in Point 2, still open) — it can over-fire on captures where Basic ID and auth messages legitimately arrive in different beacons.
4. **The replay/physical-validation boundary** (RFC 9575 §6.3 requirement 4 — cross-checking a signed position against radar/visual observation) is explicitly out of reach for a file-based Python observer and was never claimed to be implemented; worth stating explicitly in any certification narrative.
